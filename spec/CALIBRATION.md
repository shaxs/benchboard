## Execution ceiling policy (candidate.5)

The execution ceiling is a per-run declared safety bound, not an expected duration and not a global benchmark constant. The canonical field is timeCeilingMinutes in the seeded run manifest; timeCeilingSeconds is derived from it and may never disagree. The ceiling is immutable once the official clock starts: runner/supervise.mjs reads it from the manifest rather than the launch call, rejects a launch-time value that disagrees, and rejects evidence if the manifest ceiling changed during execution. A reset re-seeds the same declared ceiling and is refused while a run is active.

Runtime is now an observed benchmark result. The original 30-60 minute expectation and the 75-minute ceiling were pre-calibration design assumptions recorded in spec/BENCHMARK.md, which remains the byte-preserved historical anchor; this document supersedes them as live methodology. Nothing in the workload, hidden evaluator or scoring changes with the ceiling, and no quality points are awarded for a larger or smaller ceiling.

Quality is nevertheless conditional on the declared ceiling, because additional available time can permit more engineering work to complete. Every quality result must be reported with its declared ceiling and observed wall time beside it. Directly compared formal experimental runs require the same declared ceiling: the persistent-versus-fresh A/B must not pair fresh=180 with persistent=75. comparability() in evaluator/report.mjs returns FORMAL only for a matching candidate identity and matching declared ceilings; assertFormalComparison() throws otherwise. Mixed-ceiling sets remain analysable and plottable but are labelled DESCRIPTIVE / NON-CONTROLLED, and plots use absolute elapsed minutes on a shared axis rather than normalising each run by its own ceiling.
